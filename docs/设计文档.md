# Pulse 脉搏 · 设计文档

> 版本：v1.0 ｜ 适用范围：Pulse 团队协作与项目管理平台（后端 Spring Boot + 前端 Next.js 单仓库）
> 本文档描述产品的目标、领域模型、权限模型与关键设计决策，技术实现细节见《技术文档》。

---

## 1. 产品定位与目标

Pulse 是一个面向中小型团队的**协作式项目管理平台**，以「看板 + 任务 + 迭代 + 报表」为核心，帮助团队在同一工作区内完成从规划到交付的闭环。设计目标：

- **统一工作区**：项目、任务、迭代、成员集中管理，避免工具割裂。
- **实时协作**：看板拖拽、字段变更、在线成员/编辑态即时广播，降低协作摩擦。
- **数据安全与隔离**：团队级多租户隔离 + 系统级管理员全局视图，权限最小化。
- **可自托管**：单 JAR + 前端静态资源一体化部署，配套 Docker Compose 一键上线。
- **AI 增强（用户主权）**：AI 能力由用户自带 LLM Key 驱动，平台不持有任何第三方密钥。

### 1.1 核心能力地图

| 域 | 能力 |
|---|---|
| 认证与账户 | 注册/登录/刷新、找回密码、改密、个人资料、首次登录强制改密 |
| 团队与成员 | 创建团队、成员增删、按团队设置角色（用户/组长）、成员列表 |
| 项目管理 | 项目 CRUD、归档/恢复、状态流转、看板列（Columns）、自定义字段、保存视图 |
| 任务 | 任务 CRUD、子任务、依赖、标签、附件、评论、活动日志、批量操作、看板拖拽 |
| 迭代 | 迭代（Iteration）规划与追踪 |
| 报表 | 项目进度、成员效率、燃尽图、全局报表 |
| 通知 | 站内通知（实时推送） |
| 实时协作 | 看板在线成员、谁在编辑、任务移动/更新广播 |
| AI | 用户自带 LLM Key 的智能解析/生成（per-user，密钥加密存储） |
| 管理后台 | 系统管理员全局视图：用户管理、跨团队任务/项目、审计日志 |

## 2. 领域模型

### 2.1 核心实体与关系

```
User ───< TeamMember >─── Team ───< Project ───< Task
                                  │              │
                                  │              ├──< TaskDependency
                                  │              ├──< Tag / TaskTag
                                  │              ├──< BoardColumn
                                  │              ├──< CustomField / CustomFieldValue
                                  │              └──< SavedView
                                  └──< Iteration
Task ───< TaskComment / TaskAttachment / TaskActivityLog
User ───< Notification / AuditLog / UserLlmConfig / BurnDownSnapshot
```

### 2.2 关键实体职责

| 实体 | 表 | 职责 |
|---|---|---|
| `User` | `users` | 账户与身份；`is_system_admin` 标记系统管理员；`enabled` 账户启用态；`must_change_password` 首次改密 |
| `Team` | `teams` | 团队容器，多租户边界 |
| `TeamMember` | `team_members` | 用户与团队的从属关系 + 团队内角色 `role`（`USER`/`LEAD`） |
| `Project` | `projects` | 项目，归属某团队；`status` 含 `deleted`（软删除） |
| `Task` | `tasks` | 任务，可设父任务（子任务）、负责人、状态、优先级、到期、顺序 |
| `TaskDependency` | `task_dependencies` | 任务依赖关系 |
| `Iteration` | `iterations` | 迭代周期 |
| `Tag` / `TaskTag` | `tags` / `task_tags` | 标签及其与任务的关联 |
| `BoardColumn` | `board_columns` | 看板列（含排序） |
| `CustomField` / `CustomFieldValue` | `custom_fields` / `custom_field_values` | 自定义字段及取值 |
| `SavedView` | `saved_views` | 保存的看板视图 |
| `TaskComment` / `TaskAttachment` / `TaskActivityLog` | — | 评论 / 附件 / 活动日志 |
| `Notification` | `notifications` | 站内通知 |
| `AuditLog` | `audit_logs` | 敏感操作审计 |
| `BurnDownSnapshot` | `burn_down_snapshots` | 燃尽图快照（定时采集） |
| `UserLlmConfig` | `user_llm_configs` | 用户自带 LLM Key（加密存储） |

> 注：`TeamMember.role` 仅表示**团队内**角色；系统管理员是跨团队的全局身份，见第 3 节。

## 3. 角色与权限模型（设计核心）

Pulse 采用**双轴权限模型**，将「团队内角色」与「全局管理员」解耦：

| 维度 | 取值 | 作用域 | 存储 |
|---|---|---|---|
| 团队内角色 | `USER`（用户）/ `LEAD`（组长） | 单个团队 | `team_members.role` |
| 全局管理员 | 是 / 否 | 跨所有团队 | `users.is_system_admin` |

### 3.1 三种角色语义

| 角色 | 命名 | 能力 |
|---|---|---|
| **用户** | `USER` | 团队普通成员：执行任务、查看项目/迭代/成员/标签，无管理动作 |
| **组长** | `LEAD` | 团队内近乎全权：成员、项目、迭代、任务、标签管理；**不跨团队、不管账号** |
| **管理员** | `is_system_admin=true` | 系统级全局权限：上帝视角跨团队查询、用户启用/禁用、重置密码、审计日志；可替代任意团队的 LEAD 操作 |

### 3.2 判定规则（设计约束）

- **团队管理权** = `系统管理员` **或** `本团队 LEAD`。由 `AuthorizationService.requireTeamLead(teamId)` 统一判定，越权操作抛 `BusinessException("需要管理员权限")`。
- **系统管理员 ≠ 团队 LEAD**：管理员不自动成为任何团队的队长；LEAD 也不具备跨团队权限。
- **最后一名队长保护**：降级/移除团队唯一 `LEAD` 被拒绝（防团队失去管理员）。
- **最后一名系统管理员保护**：将唯一管理员降级为普通用户被拒绝（防系统失去管理员）。
- 前端全局角色仅暴露「用户 / 管理员」两档（组长为团队内概念，在团队设置中管理），避免概念混淆。

### 3.3 设计取舍

- 为何不把管理员做成 `team_members.role` 的一个值？管理员是**跨团队**的全局身份，与「按团队」的成员角色本质不同；混用会导致权限模型失真（例如一个用户在不同团队应是不同角色，但管理员是统一的）。
- 为何保留两套判定而非单一 `role` 列？团队内角色天然是多对多（同一用户在不同团队可不同），无法用用户级单列表达；故团队角色落 `team_members`，全局身份落 `users`。

## 4. 多租户（团队隔离）设计

- **隔离边界**：团队（`teams`）是数据隔离的一级边界。绝大多数业务查询以 `team_id` 为过滤条件。
- **上下文传递**：团队上下文通过请求头 `X-Team-ID` 传递；`TenantInterceptor` 校验该团队是否属于当前用户，并写入 `TenantContext`（ThreadLocal）。
- **上帝视角**：系统管理员可传 `X-Team-ID: all` 开启全局视图（`TenantContext.isGodView()`），绕过 `team_id` 过滤做跨团队查询；普通成员无此能力。
- **纵深防御**：除拦截器外，Service 层（如 `TaskService`、`TeamService`）对关键操作再校验租户归属，避免越权。

## 5. 安全设计原则

Pulse 的安全基线（上线审计后确立）：

1. **无默认密钥（fail-fast）**：`JWT_SECRET`、`PULSE_ENCRYPTION_KEY`、`MYSQL_ROOT_PASSWORD` 缺失即启动失败，杜绝弱口令/公开密钥裸奔。
2. **初始管理员随机口令**：首次启动由 `AdminInitRunner` 生成随机强口令并仅打印一次到日志，强制首次登录改密；不再使用任何固化的默认账号。
3. **凭证加密存储**：用户自带 LLM Key 以 AES-256-GCM 加密落库，主密钥通过环境变量注入。
4. **传输安全**：全站 HTTPS（nginx 终止 TLS），明文 80 强制跳转；实时通道经 `wss:`；启用 HSTS、CSP 等响应头。
5. **无状态认证**：JWT（HS256，access + refresh）；refresh token 仅存于 `HttpOnly + Secure + SameSite` Cookie。
6. **最小放行**：Swagger/OpenAPI 默认关闭，仅 `SWAGGER_ENABLED=true` 时放行；`/ws/**` 由 `RealtimeChannelInterceptor` 做 JWT 鉴权与团队隔离。
7. **账户保护**：禁用账户被 `JwtAuthFilter` 直接拒绝；认证接口固定窗口限流。

## 6. 实时协作设计

- **通道**：基于 Spring WebSocket + STOMP + SockJS，端点 `/ws`，SockJS 降级兼容。
- **主题**：
  - `/topic/board.{projectId}`：看板任务移动/更新广播。
  - `/topic/board.{projectId}.presence`：在线成员。
  - `/topic/board.{projectId}.edit`：谁在查看/编辑某任务。
  - `/topic/notifications.{userId}`：个人通知。
- **鉴权**：CONNECT 阶段从 `Authorization: Bearer` 解析 JWT 并设置 Principal；SUBSCRIBE 阶段校验订阅者是否属于项目所在团队（看板）或即为本人（通知），越权订阅被拒绝。
- **协同语义**：presence（在线）、edit（编辑指示）、move/update（变更广播），让多端看板即时同步。

## 7. 关键业务流程

### 7.1 注册 → 建团队 → 协作
1. 用户注册（邮箱+密码，密码 BCrypt 哈希）。
2. 创建团队：创建者自动成为该团队的 `LEAD`。
3. LEAD 添加成员（可指定角色 `USER`/`LEAD`），分配项目与任务。

### 7.2 认证与会话
1. `POST /api/v1/auth/login` → 返回 `accessToken`（Bearer）+ `refreshToken`（HttpOnly Cookie）。
2. 后续请求带 `Authorization: Bearer <accessToken>` + `X-Team-ID`。
3. access 过期用 `/refresh`（读 Cookie）无感续期。

### 7.3 管理后台（系统管理员）
1. 用户管理：启用/禁用、重置密码、设置全局角色（用户/管理员）。
2. 跨团队：查看/搜索全部任务、项目、成员。
3. 审计：查看敏感操作日志（成员管理、团队设置、项目增删、管理员操作）。

## 8. 非功能性需求

| 维度 | 设计目标 |
|---|---|
| 可部署性 | 单 Fat JAR（后端）+ 内嵌前端静态资源；Docker Compose 一键上线 |
| 可用性 | 容器 `restart: unless-stopped`；DB/App 健康检查探活 |
| 数据安全 | 团队隔离 + 加密存储 + 审计日志 |
| 性能 | HikariCP 连接池（最大 20）、MyBatis-Plus 分页、响应压缩 |
| 可观测 | Actuator 仅暴露 `/actuator/health` |
| 可维护 | 分层清晰（Controller/Service/Mapper）、统一响应与异常处理、审计日志 |

### 8.1 部署架构设计取舍

Pulse 选择 **「前端静态导出 + 内嵌 JAR」** 而非「前后端分离双服务」：

- **前端静态导出**：Next.js 配置 `output: export`，构建产物为纯静态文件（无 Node 运行时依赖），天然适合被任意静态服务器托管。
- **内嵌进 JAR**：构建脚本将 `frontend/out` 同步进 `src/main/resources/static/`，随 `mvn package` 打进 Fat JAR。运行期由 Spring Boot 内嵌 Tomcat 直接以静态资源方式返回，**前后端同源同端口**，免跨域、免额外进程。
- **收益**：生产部署只需一个 Java 进程（`java -jar pulse-1.0.0.jar`），运维面最小化；Node.js 仅在「改代码后重新构建前端」时才需要。这是「可自托管、一键上线」目标的核心支撑（详见《技术文档》§7.3）。
